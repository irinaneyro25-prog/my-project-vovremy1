# Облачная версия «Вовремя»

Первая миграция создаёт таблицу задач. Права выданы явно для роли
`authenticated`. RLS проверяет владельца при чтении и при каждой записи.
Один и тот же идентификатор задачи может существовать у разных пользователей:
повторная загрузка файла должна вставлять записи с `ON CONFLICT (owner_id, id)
DO NOTHING`. Время хранится как `timestamptz`, часовой пояс задачи — отдельно.

Код приложения поддерживает явное подключение Supabase на основном адресе
и на странице `/preview/`. После включения
облака браузер покажет вход и не переключится на локальный список при
ошибке сервиса. Локальные задачи остаются в браузере. Их можно скачать и
перенести в аккаунт через «Настройки» после подтверждения количества.
Повторный импорт пропускает задачи с теми же идентификаторами.

В проекте Vovremy
18 ноября 2026 пользователь выполнил SQL через SQL Editor и увидел
`Success. No rows returned`. Таблица появилась в Table Editor с четырьмя
политиками. Проверочный запрос показал `relrowsecurity = true`, право
`SELECT` для `authenticated = true` и для `anon = false`.
Открытая регистрация выключена и это проверено после обновления страницы.
Личный пользователь создан через кабинет. Site URL установлен на
`https://irinaneyro25-prog.github.io/my-project-vovremy1/` со слов
пользователя. SQL Editor применил схему напрямую, поэтому запись в истории
миграций Supabase может отсутствовать. Повторно выполнять файл создания
таблицы не следует. На реальном Data API проверены вход и синхронизация
задач между компьютером и iPhone. Временный второй аккаунт видел пустой
список и не видел задачи личного аккаунта; личный аккаунт не видел задачу
второго. Второй аккаунт после проверки удалён. Прямые попытки записи
в чужую задачу из отдельного клиента не выполнялись.
Файл `tests/planner_tasks_access.sql` проверяет правила в отдельной тестовой
базе после миграции. Для него нужны роли `anon` и `authenticated` и схема
`auth` из Supabase. Он откатывает свои тестовые данные.

## Условия бесплатного старта

На 18 ноября 2026 по документации Supabase у Free два проекта, 500 МБ базы
на проект и 500 000 вызовов Edge Functions в месяц. Один запуск каждую
минуту даёт до 44 640 вызовов за 31 день. Минутный запуск поддержан в
документации Supabase Cron. Доступность Cron и лимиты важно сверить для
конкретного проекта при включении.
[Лимиты](https://supabase.com/docs/guides/platform/billing-on-supabase)
[Расписание](https://supabase.com/docs/guides/functions/schedule-functions)

Малоактивный проект Free могут приостановить после семи дней низкой
активности. При остановленном проекте нельзя рассчитывать на облачные
напоминания. Cron нужен для работы приложения, а не для поддержания активности.
[Условия эксплуатации](https://supabase.com/docs/guides/deployment/going-into-prod)

Для Free документация рекомендует выгружать базу через Supabase CLI
`db dump` и хранить копии вне сервиса. Доступ к автоматическим ежедневным
копиям начинается с Pro. После подключения нужна пробная выгрузка и проверка
восстановления в отдельной базе.
[Резервные копии](https://supabase.com/docs/guides/platform/backups)

## Telegram

Файл `migrations/20261118090000_telegram.sql` создаёт закрытые таблицы
привязки и отправок. Он применён в рабочем Supabase вместе с миграциями
дополнительных прав и пропуска старых напоминаний. Обработчик
`functions/telegram/index.js` хранит всю работу с токеном бота на стороне
Supabase. После настройки секретов вошедший пользователь получает ссылку
на бот и нажимает «Старт». Ссылка действует 10 минут. Облачный обработчик
забирает напоминания по расписанию, проверяет актуальное состояние задачи
перед отправкой и учитывает завершение, перенос, удаление и отключённые
напоминания. Обычные параллельные запуски исключаются захватом записей
в PostgreSQL. При неоднозначной ошибке после успешной отправки Telegram
повтор может привести к дублю, поскольку Telegram не принимает ключ
идемпотентности для `sendMessage`.

Для Edge Function нужны значения `TELEGRAM_BOT_TOKEN`,
`TELEGRAM_BOT_USERNAME`, `TELEGRAM_WEBHOOK_SECRET` и `TELEGRAM_JOB_KEY`.
Вводите их только в **Supabase → Edge Functions → Secrets**. Значения
в файл, GitHub или чат не записываются. `TELEGRAM_JOB_KEY` также должен
храниться в Supabase Vault под именем `vovremya_telegram_job_key`.
Функция развернута, секреты сохранены в Supabase, расписание из
`telegram-cron.sql` создано и запускается раз в минуту. При первом запросе
привязки обработчик сам задаёт защищённый webhook Telegram. На iPhone
проверены привязка и синхронизация, а с закрытым сайтом — отправка сообщения
с названием задачи. Проверка отмены 18 ноября: задача на 19:58 с
напоминанием за 5 минут была сразу завершена, сообщение в 19:53 не пришло.
Это пользовательская проверка; отдельный запрос к таблице отправок после
неё не выполнялся. Ссылка в сообщении функции указывает на основной адрес.

## Дальнейшая проверка

1. При необходимости проверить прямую попытку записи в чужую задачу через
   Data API; чтение между двумя аккаунтами уже проверено на реальном проекте.
2. Перед выпуском основной версии сохранить свежую копию облачных задач и
   убедиться, что основной адрес после публикации видит те же задачи.
3. После выпуска проверить ссылку из нового сообщения Telegram: она должна
   открывать облачные задачи на основном адресе.
